From a request to an approved plan.

Keep this guide beside the operator console. Practise the complete request → new plan → compare → approve sequence on the local fixture server. Send and observe are a separate Compose rehearsal when a current-window activity is eligible. Repair needs a real execution event.

Before the call

  1. In one terminal, run CONSTELLATION_FUTURE_ADMISSION_LEAD_HOURS=1 backend/.venv/bin/python development/dev_api.py fleet_optimized from the Constellation OS checkout. In another, run cd frontend && npm run dev -- --host 127.0.0.1 --port 4173. The local server creates a fresh demo database and starts its planning worker. The one-hour admission lead applies only to this practice process.
  2. Open the local console, use the development identity chooser to sign in as a tenant admin, and open world-fleet revision 3. Use a tenant identity, not the platform login. This fixture’s clock is parked at 31 July 2026, 08:00 UTC.
  3. Choose a rehearsed customer, target and sensor. For a concrete target, try 26.2685° N, 74.3688° E and a deadline of 1 August 2026, 02:00 UTC; the fixture has opportunities at that target. Keep the deadline beyond the displayed admission lead and inside the 31 July–1 August planning window. Note the starting optimized revision for Compare. Confirm the API and console load before the call.

Live route

01

Queue the request

In Plan, select Queue request. Choose the customer; enter a justification, target name and coordinates, sensor, mission use, deadline, SLA, priority and planner value. Select Review request, check the summary, then acknowledge and select Submit request.

Show: the acceptance receipt and the new revision. Say that this is durable unscheduled demand; no collection has been scheduled yet.

02

Make a new proposed plan

Use the planning-job snippet below in the console tab’s developer tools. Keep world-fleet and enter the exact new revision shown after intake. Run opportunity_generation, wait for its successor, then run optimization on that successor. These are two distinct queued jobs. A 202 response means admitted or deferred, not completed.

Show: each job ID and the resulting revision printed by the snippet. Refresh the console and select the new optimized revision.

03

Inspect the difference

Use Compare to place the earlier optimized revision beside the new one. Point to changed or refused requests, activity placement, station use and the money figures in Economics. If the new request is infeasible, show its typed rejection reason; an accepted request does not guarantee a scheduled activity.

04

Approve the exact revision

As the tenant admin, select Review and approve. Read the pending request/activity diff and net-value change, acknowledge it, then approve this revision. A regular operator can submit work but cannot approve. Approval authorizes the chosen version; it does not contact C2.

05

Explain the send gate; rehearse it separately

On a current-window Compose plan, select an eligible activity and use Send selected activity → Request dispatch. In Execution, wait for command and observation receipts. A dispatch request is not an uplink or execution outcome; only later receipts establish those facts. In the fixture practice above, stop at approval: there is no Yamcs dispatch worker.

Planning job trigger

The current operator UI does not have a general “run planner” or “run repair” button. While signed in to http://127.0.0.1:4173, open that tab’s developer console, edit startVersion, then paste this. The script uses your existing same-origin session and CSRF cookie; run it only against the local demo tenant.

(async () => {
  const book = "world-fleet"; // scenario ID shown in Queue request
  const startVersion = 4;     // new revision shown after intake; edit if needed
  const kinds = ["opportunity_generation", "optimization"];
  // For repair after a real event: use ["repair"] and its current version.
  const csrf = document.cookie.split("; ").find(x => x.startsWith("constellation_csrf="))?.split("=")[1];
  if (!csrf) throw new Error("Sign in to the local operator console first");
  const read = async path => {
    const response = await fetch(path, { credentials: "same-origin" });
    const body = await response.json();
    if (!response.ok) throw new Error(JSON.stringify(body));
    return body.data;
  };
  let expected = startVersion;
  for (const kind of kinds) {
    const path = `/api/v1/scenarios/${encodeURIComponent(book)}/versions`;
    const versions = await read(path);
    const latest = versions.reduce((a, b) => a.version > b.version ? a : b);
    if (latest.version !== expected) throw new Error(`Expected revision ${expected}, found ${latest.version}; check the selected plan`);
    const response = await fetch(`${path}/${latest.version}/jobs`, {
      method: "POST", credentials: "same-origin",
      headers: { "Content-Type": "application/json", "X-CSRF-Token": decodeURIComponent(csrf) },
      body: JSON.stringify({ action_id: crypto.randomUUID(), job_kind: kind,
        expected_scenario_version: latest.version,
        expected_scenario_hash: latest.canonical_hash,
        justification: "Mentor demo: plan accepted request" })
    });
    const submitted = await response.json();
    if (!response.ok) throw new Error(JSON.stringify(submitted));
    const id = submitted.data.job_id;
    console.log(`${kind} queued`, id, submitted.data.admission);
    let completed = false;
    for (let attempt = 0; attempt < 450; attempt++) {
      const state = await read(`/api/v1/jobs/${id}`);
      if (state.payload.status === "failed") throw new Error(JSON.stringify(state.payload.failure));
      if (state.payload.status === "succeeded") {
        const successor = (await read(path)).find(v => v.canonical_hash === state.payload.output_hash);
        if (!successor) throw new Error(`Job ${id} succeeded but its successor was not found`);
        console.log(`${kind} succeeded → revision ${successor.version}`, successor);
        expected = successor.version;
        completed = true;
        break;
      }
      await new Promise(resolve => setTimeout(resolve, 2000));
    }
    if (!completed) throw new Error(`Job ${id} is still running; inspect /api/v1/jobs/${id}`);
  }
})().catch(error => console.error("Planning stopped:", error));

If a job fails: read its printed failure and the job record at /api/v1/jobs/<job-id>. Do not approve an old revision or claim the plan succeeded. A stale input or infeasible request may require a different rehearsed case.

Replan or repair

New request or changed planning input → replan

From the accepted request’s latest unscheduled revision, run opportunity_generation followed by optimization as above. Compare the earlier optimized version with the new proposed version. This is the reliable path for a fresh request; intake itself never queues either job.

Execution disruption → repair

First show an actual missed, failed or changed execution event in Execution. On the affected scenario, take its current optimized/authorized revision as startVersion, change kinds to ["repair"], and run the same snippet. Repair needs a valid baseline and event evidence; without those, it can fail closed. Compare the repair successor, inspect its changed commitments and money report, then approve that exact revision. Request dispatch only if an eligible remaining activity and a live C2 worker exist. Open repair in Execution navigates to an existing repair result; it does not start the job.

Fallback if time is short: finish at the approval receipt. For repair, open an already generated repaired revision and say plainly that its disruption was prepared. Avoid resetting Compose volumes during the meeting.

Thirty-second talk track

“A customer asks for an observation. We keep that request as its own version before scheduling anything. The planner generates physical opportunities, then chooses collections and ground contacts under resource and deadline limits. I can compare what moved and what it costs. A human approves one exact version; sending an activity is a second decision. In the Compose integration, Yamcs and the simulator return receipts, so an execution failure can feed a repair.”
